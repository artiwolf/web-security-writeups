# SSRF Write-up

## Резюме (Executive Summary)
На странице товара есть функция "Check stock", которая по URL из параметра stockApi обращается к внутреннему сервису и возвращает информацию об остатках. Разработчики знали про SSRF и поставили защиту в виде whitelist - сервер разрешает обращаться только к хосту stock.weliketoshop.net, всё остальное отклоняется с ошибкой.

Whitelist на первый взгляд выглядит понадёжнее blacklist'а, но проблема оказалась не в списке разрешённых хостов, а в том, как сервер вообще разбирает переданный URL. Оказалось, что синтаксис embedded credentials в URL (часть перед @) воспринимается как имя пользователя, а не как хост - и именно хост после @ и проверяется по whitelist'у. Дальше выяснилось, что если добавить в "имя пользователя" символ # в закодированном виде, сервер, который реально ходит по URL, и сервер, который его валидирует, расходятся в интерпретации - и итоговый запрос уходит совсем не туда, куда его отправили.

В итоге получилось обратиться к внутренней админке по localhost и удалить пользователя carlos - формально URL для проверки выглядел легитимным (указывал на разрешённый хост), а по факту запрос ушёл на внутренний ресурс. Уровень риска - высокий: SSRF с доступом к localhost-сервисам обычно даёт прямой путь к внутренним админкам, метаданным облака и другим ресурсам, недоступным напрямую снаружи.

## Методология
Порядок действий - постепенное определение того, как именно устроена проверка whitelist'а:
- Перехват запроса от функции "Check stock" в Burp и определение, что stockApi - это полноценный URL, по которому сервер сам ходит на бэкенд.
- Прямая попытка подставить localhost - запрос отклонён с сообщением о том, что разрешён только stock.weliketoshop.net.
- Проверка, как парсер URL относится к синтаксису с embedded credentials (username@host) - подстановка user@stock.weliketoshop.net прошла проверку.
- Проверка, можно ли аналогичным образом использовать localhost в качестве "имени пользователя" перед разрешённым хостом - сходу не сработало из-за символа #, обрывающего URL.
- Подбор варианта с закодированным символом # (%2523), чтобы обойти расхождение между тем, что видит валидатор, и тем, куда реально уходит запрос.
- Сборка финального payload'а, ведущего на localhost/admin с параметрами удаления пользователя carlos.

## Описание уязвимости
### Общие сведения
| | |
| --- | --- |
| Тип уязвимости | Server-Side Request Forgery (SSRF) с обходом whitelist-фильтра через некорректный парсинг URL |
| Класс | CWE-918 |
| Точка внедрения | POST-параметр stockApi в запросе /product/stock |
| Требуемые привилегии | Отсутствуют (неаутентифицированный пользователь) |

### Почему whitelist не сработал
URL-синтаксис допускает конструкцию вида http://username@host/, где всё, что стоит до @, - это не хост, а данные для HTTP Basic Auth (имя пользователя), и именно host после @ должен использоваться для соединения.

А также, закодированный символ %2523 (#) в позиции "имени пользователя" ведёт себя по-разному в зависимости от того, какая часть системы и на каком этапе его декодирует. Для валидатора, который смотрит на URL один раз, строка после @ всё ещё выглядит как разрешённый хост, а для компонента, который реально выполняет запрос и декодирует URL иначе, символ # обрывает адрес раньше и превращает всё, что было до него (включая нужный нам localhost), в реальный хост назначения. Из-за этого расхождения в интерпретации одного и того же URL двумя разными частями приложения и получается обход.

### Шаг 4. Проверка обрыва URL через #
Добавлен незакодированный символ # после localhost, чтобы посмотреть, получится ли просто "отрезать" URL на нужном месте:

Запрос был отклонён - в незакодированном виде # сразу превращает остаток строки во фрагмент URL, из-за чего хост становится некорректным ещё на этапе базовой валидации.

### Шаг 5. Обход через закодированный %2523
Замена # на его URL-кодированную версию %2523:

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file34.png)

На этот раз запрос прошёл проверку и ушёл именно на localhost - валидатор декодирует URL один раз и видит "легитимный" хост stock.weliketoshop.net после @, а компонент, реально выполняющий запрос, раскодирует %2523 в # уже на своём этапе и обрывает адрес раньше, воспринимая localhost:80 как настоящий хост назначения.

### Шаг 6. Сборка финального payload'а и удаление пользователя
Собран итоговый URL, ведущий на внутреннюю админку с параметрами удаления пользователя carlos:

Сервер выполнил запрос в контексте внутренней сети, пользователь carlos был удалён, лаборатория показала статус Solved.

## Влияние на бизнес (Impact)
- Атакующий может обращаться от имени сервера к внутренним ресурсам, недоступным напрямую снаружи. В частности, к внутренним админ-панелям.
- В данном случае удалось выполнить действие с реальными последствиями (удаление пользователя) без какой-либо аутентификации в самом приложении.
- Whitelist-фильтрация URL сама по себе не гарантирует защиту, если разные компоненты системы по-разному разбирают один и тот же URL - расхождение в парсинге сводит на нет любую проверку по строке.
- В боевой инфраструктуре аналогичная техника часто применяется для доступа к внутренним сервисам облака (метаданные, service discovery), что может привести к куда более серьёзной компрометации, чем в рамках учебной лаборатории.

## Рекомендации по устранению (Remediation)
### Основная рекомендация
Не полагаться на разбор и валидацию URL как на единственный механизм защиты от SSRF. Правильный подход - использовать сетевую сегментацию: бэкенд, выполняющий такие запросы, физически не должен иметь сетевого доступа к внутренним ресурсам (админкам, метаданным облака и т.д.)

### Дополнительные меры
- Использовать единый, проверенный и хорошо протестированный URL-парсер на всех этапах обработки запроса (и в валидаторе, и в компоненте, выполняющем запрос), чтобы исключить расхождение в интерпретации одного и того же URL.
- Резолвить хост из URL до отправки запроса и проверять полученный IP-адрес на принадлежность к приватным/локальным диапазонам, а не полагаться только на строковую проверку хоста.
- Отключить поддержку избыточных возможностей URL-синтаксиса (embedded credentials, необычные схемы) там, где приложению они не нужны для легитимной работы.
- Использовать allowlist не по хосту в URL, а на уровне сетевого firewall - тогда даже успешный обход валидации на уровне приложения не даст реального сетевого доступа к запрещённым адресам.

## Заключение
Whitelist звучит надёжно, но реальная надёжность зависит от деталей парсинга URL, а не от самого факта наличия белого списка. Расхождение в том, как один и тот же URL интерпретируют разные части системы (одна - для проверки, другая - для реального похода по адресу), оказалось достаточным, чтобы полностью обойти защиту. Для реального приложения такая уязвимость особенно опасна, потому что даёт доступ именно туда, куда обычно и целятся такие атаки - во внутреннюю сеть и админ-интерфейсы, недоступные извне.
