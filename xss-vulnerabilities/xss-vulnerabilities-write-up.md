# XSS Write-up

## Резюме (Executive Summary)
На сайте найдено поле поиска, значение которого возвращается обратно на страницу без нормальной обработки. Это классическая reflected XSS, но с усложнением: разработчики поставили фильтр, который вырезает опасные вещи. Разрешены только некоторые HTML-теги из "белого списка", а все обработчики событий (onclick, onerror, onload и т.д.) и атрибут href у ссылок - блокируются.

Обычные payload'ы не проходят фильтр. Но есть способ обойти защиту через SVG-анимацию, которая позволяет менять атрибут href в обход прямого запрета.

В итоге удалось выполнить произвольный JavaScript в браузере условной жертвы, просто заставив её кликнуть по элементу на странице. Уровень риска - высокий, потому что XSS такого рода можно использовать для кражи cookie, сессии пользователя, или выполнения действий от его имени.

## Методология
Порядок действий был такой - сначала простое исследование, потом постепенный обход защиты:
- Проверка, куда попадает значение из строки поиска - оно вставляется прямо в HTML-код страницы без экранирования.
- Тестирование стандартного payload'а для XSS - сервер ответил, что тег запрещён ("Tag is not allowed").
- Перебор через Burp Intruder списка всех существующих HTML/SVG-тегов (взято из XSS Cheat Sheet на сайте PortSwigger) и определение по ответу сервера, какие теги разрешены.
- Проверка, можно ли использовать обработчики событий (onclick, onfocus и т.д.) - все они тоже блокируются фильтром.
- Нахождение обходного пути через SVG-тег <animate>.

### Почему фильтр не спасает
Разработчики закрыли самые очевидные способы вставить JavaScript - события (onerror, onclick и подобные) и прямую подстановку javascript: в href. Проблема в том, что в HTML/SVG есть тег <animate>, который умеет менять любой атрибут элемента во время анимации, включая href - и делает это не через событие, а через собственный механизм SVG-анимации. Фильтр блокирует href как обычный атрибут, но не понимает, что через <animate attributeName=href> можно установить его динамически, в обход прямой проверки.

Получается, что вместо ссылки с javascript: в href, мы "дорисовываем" этот href через анимацию - и в глазах фильтра это выглядит безобидно, а в браузере всё равно срабатывает как клик по javascript-ссылке.

Дальше в самой лаборатории нужно было доставить этот payload эмулированному пользователю ("жертве") - это делается через встроенную функцию доставки эксплойта (Deliver exploit to victim) в интерфейсе лаборатории. После того как виртуальный пользователь перешел по ссылке, лаборатория показала статус Solved.

## Влияние на бизнес (Impact)
- XSS позволяет выполнить любой JavaScript в браузере жертвы от имени сайта, на котором сработал payload.
- Через это можно украсть cookie сессии и зайти в аккаунт пользователя без пароля.
- Можно показать жертве поддельную форму логина и увести у неё логин/пароль.
- Можно выполнять действия от имени жертвы на сайте.

## Рекомендации по устранению (Remediation)
### Основная рекомендация
Белые списки тегов и атрибутов - это правильный подход в целом, но список нужно тестировать намного шире, включая менее известные SVG/HTML-теги вроде animate, animatetransform, set и подобные, которые тоже могут менять атрибуты элементов.

### Дополнительные меры
- Экранировать спецсимволы (<, >, ", ', &) при выводе пользовательских данных в HTML - это базовая защита, которая закрывает большую часть XSS сразу.
- Использовать проверенные библиотеки вместо самописного фильтра - у них уже учтены такие обходы.
- Добавить заголовок Content-Security-Policy (CSP), который ограничивает, что вообще может выполняться на странице.
- Если есть возможность - вообще не вставлять пользовательский ввод как HTML, а показывать его как обычный текст (textContent, а не innerHTML).
- Периодически тестировать фильтр заново - списки тегов и обходов постоянно обновляются.

## Заключение
Эта лаборатория хорошо показывает, что фильтр по белому списку - это не одна проверка, а много мелких деталей, и достаточно упустить один тег или один способ выставить атрибут - и вся защита обходится. Здесь разработчики закрыли самые популярные способы (события, href), но не учли, что через SVG-анимацию можно добиться того же эффекта другим путём. Для реального приложения это была бы критическая уязвимость: несложный клик пользователя по ссылке - и злоумышленник получает контроль над его сессией.
