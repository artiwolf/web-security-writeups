# XXE Write-up

## Резюме (Executive Summary)
Функция "Check stock" на странице товара принимает и разбирает XML, отправленный от клиента - классическая точка для XXE. Первая проверка стандартным внешним объектом результата не дала: сервер не отображал ответ на странице, то есть это слепая (blind) инъекция, а исходящие соединения наружу (out-of-band) на сервере тоже заблокированы - обычный способ вытащить данные через собственный listener не сработал.

Решение нашлось в более тонкой технике - "переиспользовании" уже существующего на сервере DTD-файла. Вместо того чтобы грузить свой DTD откуда-то извне, можно подключить локальный DTD, который и так лежит на файловой системе сервера (это стандартный файл, который есть на многих Linux-системах с GNOME), и переопределить в нём одну из уже объявленных сущностей так, чтобы она вызвала ошибку парсинга с содержимым нужного файла внутри текста ошибки.

В итоге удалось прочитать содержимое /etc/passwd через сообщение об ошибке парсера, без единого исходящего соединения наружу. Уровень риска - критический, потому что XXE такого рода в реальном приложении может дать доступ к произвольным файлам сервера, конфигам с секретами и потенциально - к дальнейшему продвижению по инфраструктуре.

## Методология
Порядок действий - от простой проверки к более сложной технике, когда простая не сработала:
- Перехват запроса от функции "Check stock" в Burp Proxy и анализ тела запроса - оказалось, что это XML.
- Проверка на XXE стандартным способом - добавление внешней сущности с указанием на /etc/passwd прямо в теле XML.
- Обнаружение, что ответ сервера не содержит результата разбора XML - вывод о том, что инъекция слепая (blind).
- Проверка на out-of-band канал через внешний DTD - не сработало, что указывает на блокировку исходящих соединений.
- Поиск альтернативного способа эксплуатации - через локальный DTD-файл, уже присутствующий на сервере.
- Составление payload'а с переопределением существующей сущности из локального DTD для генерации ошибки с содержимым файла.
- Отправка запроса и получение содержимого /etc/passwd в тексте ошибки.

### Почему обычный XXE не сработал и как обойти ограничение
Стандартный XXE через внешнюю сущность, указывающую напрямую на /etc/passwd, не дал результата по двум причинам: приложение не выводит результат разбора XML на страницу (то есть это слепая инъекция), а сервер к тому же не может достучаться наружу, чтобы передать данные через собственный listener атакующего - типичный внешний DTD с исходящим соединением тоже отваливается.

Выход - не тащить вредоносный DTD снаружи, а воспользоваться тем DTD-файлом, который уже лежит на файловой системе сервера. У многих Linux-систем есть предустановленные DTD-файлы (например, документация GNOME/Yelp), внутри которых объявлены свои сущности. Если подключить такой локальный файл через параметрическую сущность и переопределить одну из уже объявленных в нём сущностей, можно встроить в неё error-based полезную нагрузку - при обращении к несуществующему файлу с подставленным содержимым /etc/passwd в пути парсер выбросит ошибку, и текст этой ошибки будет содержать искомые данные.

## Ход эксплуатации (Proof of Concept)
### Шаг 1. Обнаружение точки внедрения XML
Была открыта страница товара, нажато "Check stock" и перехвачен запрос в Burp:

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file24.png)

Тело запроса оказалось обычным XML-документом с полями productId и storeId.

### Шаг 2. Проверка на стандартный XXE
В тело запроса добавлено объявление внешней сущности, указывающей на /etc/passwd, и подставлено в поле productId:

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file25.png)

Ответ сервера не содержал ни ошибки, ни содержимого файла - обычная страница без изменений. Это означало, что инъекция слепая: сервер парсит XML и, возможно, даже подставляет сущность, но результат никак не отображается.

### Шаг 3. Попытка эксфильтрации через внешний DTD
Подключен DTD с внешнего, контролируемого адреса, чтобы проверить, может ли сервер вообще выполнять исходящие запросы:

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file26.png)

Взаимодействия с внешним ресурсом не последовало - сервер либо не может выходить наружу, либо это как-то ограничено. Значит, классический blind XXE с эксфильтрацией через внешний ресурс тут не сработает, нужен другой подход.

### Шаг 4. Поиск локального DTD-файла на сервере
Раз внешние соединения не проходят, был подключен DTD-файл, который может физически лежать на файловой системе сервера. Взят известный по многим Linux-дистрибутивам путь /usr/share/yelp/dtd/docbookx.dtd и проверено, что сервер способен его прочитать без ошибки о "файл не найден":

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file27.png)

Файл существует и парсер успешно его подключил - значит, можно попробовать переопределить одну из сущностей внутри него.

### Шаг 5. Сборка payload'а с переопределением сущности
Собран финальный XML, где объявляется параметрическая сущность с путём к локальному DTD, а затем переопределяется одна из уже объявленных в этом DTD сущностей (ISOamso) так, чтобы она через вложенную конструкцию error-based XXE подставила содержимое /etc/passwd в путь к несуществующему файлу:

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file28.png)

Сначала подключается местный DTD целиком (local_dtd), затем переопределяется одна из сущностей, которая в нём реально объявлена (ISOamso) - и именно в момент этого переопределения подставляется цепочка из трёх вложенных сущностей, которая в итоге пытается открыть несуществующий путь с именем файла /etc/passwd внутри - парсер бросает ошибку, в тексте которой оказывается всё содержимое файла.

### Шаг 6. Получение содержимого файла из ошибки
Отправлен собранный запрос и получено в ответе сервера сообщение об ошибке парсинга, содержащее полное содержимое /etc/passwd:

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file29.png)

Лаборатория подтвердила решение (статус Solved).

## Влияние на бизнес (Impact)
- Атакующий может прочитать произвольные файлы на файловой системе сервера, включая конфигурационные файлы с паролями, ключами доступа и другими секретами.
- Атака работает даже при полностью заблокированных исходящих соединениях с сервера - то есть типичная защита "отключить внешний интернет для бэкенда" здесь не спасает.
- В зависимости от того, что ещё установлено на сервере, через XXE можно попытаться добраться и до внутренних сервисов (SSRF-часть XXE), расширив атаку за пределы простого чтения файлов.
- Слепой характер уязвимости не является защитой сам по себе - как показано, данные всё равно можно вытащить, просто с чуть более сложной техникой.

## Рекомендации по устранению (Remediation)
### Основная рекомендация
Отключить обработку внешних сущностей (external entities) и DTD в XML-парсере на уровне конфигурации библиотеки. Подавляющее большинство современных XML-парсеров поддерживают безопасный режим ("disallow-doctype-decl" или аналог), при котором DOCTYPE вообще не обрабатывается - это закрывает XXE полностью, а не только конкретный вектор с локальным DTD.

### Дополнительные меры
- Если приложению действительно нужен приём XML от пользователя, использовать упрощённые форматы данных (JSON) там, где это возможно, вместо XML.
- Применять принцип наименьших привилегий для процесса, обрабатывающего XML - ограничить доступ к файловой системе на уровне ОС/контейнера, чтобы даже при наличии XXE ущерб был минимальным.
- Убрать или ограничить доступ к стандартным системным DTD-файлам, которые потенциально можно "переиспользовать" для этой техники.
- Регулярно тестировать XML-обрабатывающий функционал на XXE, включая слепые сценарии и сценарии с заблокированными исходящими соединениями - как показала эта лаборатория, отсутствие явного вывода данных ещё не значит отсутствие уязвимости.

## Заключение
Эта лаборатория хорошо показывает, что "слепая" уязвимость и заблокированные исходящие соединения - это не одно и то же, что "уязвимости нет". Когда прямые пути эксфильтрации данных закрыты, всегда стоит поискать альтернативные техники - в данном случае помогло знание того, что на сервере почти наверняка есть предустановленные DTD-файлы, которые можно переиспользовать для генерации информативной ошибки. Это заметно более продвинутая техника, чем базовый XXE, и она хорошо демонстрирует, что защита "просто заблокировать исходящий трафик" не закрывает уязвимость полностью, если сам парсинг DOCTYPE не отключён.
