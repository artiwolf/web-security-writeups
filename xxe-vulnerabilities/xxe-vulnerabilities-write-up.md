# XXE Write-up

## Резюме

Функция Check stock на странице товара принимает XML-документ и передаёт его на серверную обработку. Это создаёт потенциальную точку для атаки XML External Entity (XXE). Первоначальная проверка с внешней сущностью показала, что XML-парсер может обращаться к локальным файлам, однако содержимое файла не выводится непосредственно в ответе приложения. Это соответствует сценарию blind XXE. Далее была проверена возможность получения данных через внешний ресурс. В рамках теста взаимодействия с внешним ресурсом не произошло, поэтому такой способ эксфильтрации использовать не удалось.

Для дальнейшей эксплуатации был использован локальный DTD-файл /usr/share/yelp/dtd/docbookx.dtd, уже присутствующий на сервере. Одна из объявленных в нём сущностей ISOamso была переопределена таким образом, чтобы при обработке XML возникала ошибка, в которой было содержимое /etc/passwd. В результате удалось получить содержимое /etc/passwd через сообщение об ошибке XML-парсера. Лаборатория PortSwigger подтвердила успешное выполнение задания.

## Методология

Исследование проводилось от простого сценария эксплуатации к более сложному:

1. Перехвачен запрос функции Check stock и определено, что тело запроса содержит XML.
2. Выполнена проверка стандартного XXE с обращением к /etc/passwd.
3. Установлено, что содержимое файла не возвращается непосредственно в ответе приложения.
4. Проверена возможность использования внешнего ресурса для out-of-band взаимодействия.
5. После отсутствия ожидаемого взаимодействия рассмотрен вариант с локальным DTD, уже находящимся на сервере.
6. Проверен доступ к /usr/share/yelp/dtd/docbookx.dtd.
7. В локальном DTD найдена сущность ISOamso, подходящая для переопределения.
8. Составлен payload с параметрическими сущностями, который вызывает ошибку парсера с содержимым /etc/passwd.

## Описание уязвимости

### Общие сведения

| | |
| --- | --- |
| Тип уязвимости | Blind XML External Entity Injection (XXE) с использованием локального DTD |
| CWE | CWE-611: Improper Restriction of XML External Entity Reference |
| Точка внедрения | Тело XML-запроса функции Check stock |
| Требуемые привилегии | Не требуются |

XXE возникает, когда XML-парсер обрабатывает внешние сущности, определённые в XML-документе. В зависимости от конфигурации парсера внешняя сущность может ссылаться на локальный файл или внешний ресурс.

В данной лаборатории прямое получение содержимого файла через ответ приложения невозможно, поэтому используется blind XXE. Однако наличие blind XXE не означает, что данные невозможно получить: в некоторых конфигурациях можно использовать другие каналы, например out-of-band взаимодействие или сообщения об ошибках.

## Почему стандартный XXE не дал содержимое файла

При использовании внешней сущности, указывающей на /etc/passwd, сервер обрабатывает XML и обращается к указанному файлу. Однако содержимое файла не отображается непосредственно в ответе. Вместо него приложение возвращает ошибку, связанную с некорректным значением productId.

Это происходит потому, что после подстановки сущности вместо ожидаемого числового идентификатора в productId оказывается содержимое /etc/passwd. Приложение не может обработать такое значение как идентификатор товара и возвращает сообщение об ошибке.

# Ход эксплуатации (Proof of Concept)

## Шаг 1. Обнаружение точки обработки XML

Была открыта страница товара, выбрана функция Check stock, после чего запрос был перехвачен в Burp Suite.

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file24.png)

Тело запроса содержит XML-документ с параметрами productId и storeId.

## Шаг 2. Проверка стандартного XXE

В XML была добавлена внешняя сущность, указывающая на локальный файл /etc/passwd, после чего ссылка на сущность была помещена в productId.

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file25.png)

Сервер обработал внешнюю сущность. При её подстановке в productId вместо ожидаемого числового значения оказалось содержимое /etc/passwd, после чего приложение вернуло ошибку Invalid product ID. Это подтверждает, что XML-парсер способен обрабатывать внешние сущности и обращаться к локальным файлам. При этом само содержимое /etc/passwd не отображается непосредственно в обычном ответе приложения, поэтому для получения данных требуется другой канал.

## Шаг 3. Проверка out-of-band взаимодействия

Для проверки возможности эксфильтрации через внешний ресурс был использован внешний DTD.

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file26.png)

Ожидаемого взаимодействия с внешним ресурсом не произошло.

## Шаг 4. Поиск подходящего локального DTD

Поскольку внешний канал оказался непригоден, был рассмотрен вариант использования DTD-файла, уже находящегося на файловой системе сервера. Для этого использован путь: /usr/share/yelp/dtd/docbookx.dtd
Этот файл используется в официальном решении данной лаборатории PortSwigger. В нём присутствует сущность ISOamso, которую можно переопределить в собственной внутренней DTD-конструкции.

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file27.png)

Проверка показала, что парсер может обратиться к указанному DTD-файлу. Это позволяет перейти к следующему этапу атаки.

## Шаг 5. Переиспользование локального DTD

Вместо загрузки собственного DTD извне был подключён локальный DTD через параметрическую сущность:

<!ENTITY % local_dtd SYSTEM "file:///usr/share/yelp/dtd/docbookx.dtd">

После этого была переопределена сущность ISOamso, присутствующая в подключённом DTD. Финальная конструкция использует несколько параметрических сущностей. Их задача состоит в том, чтобы:

1. Загрузить локальный DTD;
2. Переопределить ISOamso;
3. Создать сущность, которая обращается к /etc/passwd;
4. Сформировать ссылку на несуществующий файл, включающую полученное содержимое /etc/passwd;
5. Заставить XML-парсер сформировать ошибку, содержащую это значение.

То есть, данные извлекаются не через обычный ответ приложения и не через внешний сервер, а через сообщение об ошибке, сформированное XML-парсером.

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file28.png)

## Шаг 6. Получение содержимого /etc/passwd

После отправки подготовленного XML сервер вернул сообщение об ошибке, содержащее содержимое /etc/passwd.

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file29.png)

Лаборатория PortSwigger подтвердила успешное выполнение задания со статусом Solved.

# Почему сработал этот обход

Основная проблема заключается не только в возможности обращения XML-парсера к локальным файлам, но и в том, что обработка DOCTYPE, внешних сущностей и локальных DTD остаётся доступной. В обычном blind XXE отсутствие прямого вывода данных значительно усложняет эксплуатацию. Однако XML-парсер может генерировать ошибки, а некоторые ошибки содержат значения, полученные во время обработки внешних сущностей.

В данной лаборатории используется существующий DTD-файл. Его сущность ISOamso переопределяется таким образом, чтобы встроить в процесс обработки дополнительную цепочку сущностей. В результате содержимое /etc/passwd попадает в путь к несуществующему файлу и затем отображается в сообщении об ошибке. Это позволяет получить данные без необходимости отправлять их на внешний сервер.

# Влияние (Impact)

В реальном приложении последствия XXE зависят от конфигурации XML-парсера, прав процесса и доступных серверу ресурсов. Потенциальные последствия включают:

- чтение файлов, доступных процессу, который обрабатывает XML;
- раскрытие конфигурационных файлов и других чувствительных данных;
- компрометацию секретов, если они хранятся в доступных файлах;
- SSRF, если XML-парсер разрешает обращения к сетевым ресурсам;
- дальнейшее развитие атаки при наличии дополнительных уязвимостей или недостаточных ограничений доступа.

В данной лаборатории было продемонстрировано чтение /etc/passwd даже без использования внешнего канала для передачи данных.

# Рекомендации по устранению (Remediation)

## Основная мера

Необходимо отключить обработку внешних сущностей и DTD в XML-парсере, если они не требуются приложению. Конкретная настройка зависит от используемой XML-библиотеки и языка программирования. В некоторых парсерах доступны параметры, запрещающие DOCTYPE или загрузку внешних сущностей.

Безопасная конфигурация должна как минимум предотвращать:

- загрузку внешних сущностей;
- загрузку внешних DTD;
- обращение XML-парсера к локальной файловой системе через сущности;
- сетевые обращения, инициированные XML-парсером.

## Дополнительные меры

- Если XML не является обязательным форматом, рассмотреть использование JSON или другого формата, не обладающего аналогичным механизмом внешних сущностей.
- Запускать процесс, обрабатывающий XML, с минимально необходимыми правами.
- Ограничить доступ процесса к файловой системе на уровне ОС или контейнера.
- Ограничить исходящие сетевые соединения как дополнительный уровень защиты, но не использовать это как единственную защиту от XXE.
- Регулярно тестировать XML-функциональность на обычный и blind XXE.

# Заключение

Лаборатория демонстрирует, что отсутствие прямого вывода XML-данных и блокировка исходящих соединений не устраняют XXE-уязвимость. В ходе исследования сначала было подтверждено обращение XML-парсера к локальному файлу. Затем была проверена возможность out-of-band эксфильтрации, после чего выбран альтернативный способ эксплуатации через локальный DTD. Использование существующего DTD /usr/share/yelp/dtd/docbookx.dtd и переопределение сущности ISOamso позволили сформировать ошибку парсера, содержащую содержимое /etc/passwd.

Основной вывод: если приложение обрабатывает недоверенный XML и при этом разрешает DOCTYPE и внешние сущности, отсутствие видимого результата или блокировка исходящих соединений не гарантируют безопасность.
