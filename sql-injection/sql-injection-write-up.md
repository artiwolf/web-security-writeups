# Write-up SQL injection

## Резюме (Executive Summary)
В ходе прохождения лаборатории PortSwigger Web Security Academy была обнаружена SQL-инъекция в параметре category. Уязвимость позволяет злоумышленнику внедрять произвольные SQL-конструкции в запрос к базе данных и получать данные из других таблиц базы данных, включая таблицу пользователей с учётными данными.

В рамках демонстрации эксплуатации были извлечены имена пользователей и пароли всех учётных записей приложения, после чего было выполнено успешное подтверждение критичности уязвимости - вход в систему под учётной записью с максимальными привилегиями (administrator) без знания пароля в открытом виде до момента его извлечения из базы данных.

Итоговый уровень риска оценивается как Критический (Critical). Оценка приведена для учебной лаборатории и не является оценкой реальной производственной системы.

## Область и условия тестирования (Scope)
| | |
 | --- | --- |
 | Целевое приложение | Учебный интернет-магазин (демонстрационное приложение PortSwigger Web Security Academy) | 
 | Уязвимый функционал | Фильтр товаров по категории на странице каталога (параметр category) | 
 | Метод HTTP-запроса	 | GET
 | Тип тестирования	 | Black-box, аутентификация не требуется
 | Разрешение на тестирование	 | Официальная изолированная лабораторная среда PortSwigger, предназначенная для обучения
 | Ограничения | 	Тестирование производилось строго в рамках предоставленной лаборатории; иные хосты и системы не затрагивались

## Методология
Тестирование проводилось вручную с использованием Burp Suite. Шаги работы:
- Перехват и анализ HTTP-трафика приложения через Burp Proxy.
- Идентификация точки ввода, потенциально уязвимой к SQL-инъекции (параметр запроса category).
- Подтверждение факта инъекции путём отправки синтаксически некорректного и корректного payload'ов и сравнения ответов сервера.
- Определение количества столбцов, возвращаемых исходным SQL-запросом (техника ORDER BY).
- Определение столбцов с типом данных, пригодным для вывода строковых значений (техника UNION SELECT NULL).
- Построение полноценной UNION-инъекции для извлечения данных из таблицы users.
- Использование полученных учётных данных для аутентификации в приложении под привилегированной учётной записью.

## Описание уязвимости
### Общие сведения
| | |
 | --- | --- |
| Название	| SQL injection UNION attack, retrieving data from other tables
| Класс уязвимости	| CWE-89 — SQL Injection
| Точка внедрения| GET-параметр category в запросе к странице /filter
| Метод обнаружения | 	Ручное тестирование через Burp Suite Repeater
| Требуемые привилегии	| Отсутствуют (неаутентифицированный пользователь)

### Техническое описание
Функционал фильтрации товаров по категории формирует SQL-запрос к базе данных, подставляя значение параметра category напрямую в тело запроса без должной валидации и параметризации. Так как результаты выполнения запроса (наименования и описания товаров) отображаются непосредственно в теле HTTP-ответа, у злоумышленника есть возможность не только влиять на логику запроса, но и визуально получать вывод внедрённых данных - это классический сценарий для эксплуатации через UNION-based SQL injection.

## Ход эксплуатации (Proof of Concept)
### Шаг 1. Подтверждение наличия SQL-инъекции
Исходный легитимный запрос к приложению при выборе категории товаров выглядел следующим образом:

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file.png)

Для проверки на инъекцию в значение параметра было добавлено одиночное кавычка-символ, что вызвало ошибку выполнения запроса на стороне сервера (HTTP 500 Internal Server Error):

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file2.png)

Возникновение ошибки при добавлении необработанной кавычки, а также корректный ответ при экранировании кавычки (например, при использовании конструкции category=Gifts'--), подтвердило, что параметр напрямую подставляется в SQL-запрос без фильтрации.

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file3.png)

### Шаг 2. Определение количества столбцов запроса
Для построения корректной UNION-инъекции необходимо, чтобы число столбцов во внедряемом SELECT совпадало с числом столбцов в исходном запросе. Количество столбцов определялось последовательным увеличением индекса в конструкции ORDER BY до появления ошибки:

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file4.png)
![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file5.png)
![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file6.png)

Запрос с ORDER BY 3 вернул ошибку базы данных ("The ORDER BY position number 3 is out of range"), тогда как ORDER BY 2 выполнился успешно. Это позволило установить, что исходный запрос возвращает ровно два столбца.

### Шаг 3. Определение столбцов, пригодных для вывода строковых данных
Далее было проверено, какие из двух столбцов способны выводить строковые (текстовые) значения - это необходимо, чтобы впоследствии извлечь строковые данные из таблицы users:

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file7.png)

Запрос выполнился без ошибок, подтвердив, что оба столбца совместимы по типу данных с NULL. Далее NULL поочерёдно заменялся на строковый маркер:

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file8.png)
![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file9.png)

Оба варианта были выполнены успешно и строковый маркер 'a' отобразился на странице результатов, что подтвердило: оба столбца пригодны для вывода произвольных строковых значений.

### Шаг 4. Извлечение данных из таблицы users
Зная структуру целевой таблицы (users, столбцы username и password), был сформирован финальный эксплуатирующий payload, объединяющий значения обоих столбцов через разделитель для удобства чтения в едином выводимом поле:

![](https://github.com/artiwolf/web-security-writeups/blob/main/screenshots/file10.png)

Сервер вернул страницу каталога, в теле которой, помимо обычных товаров, отобразился полный список учётных данных всех зарегистрированных пользователей приложения - пары «имя пользователя / пароль» в открытом (либо демонстрационно нехэшированном) виде, в том числе учётная запись administrator.

### Шаг 5. Подтверждение критичности - аутентификация под привилегированной учётной записью
Извлечённые из ответа сервера учётные данные пользователя administrator были использованы на форме входа в приложение (login). Аутентификация прошла успешно, что подтвердило полную компрометацию учётной записи с максимальными правами в приложении и, соответственно, успешное решение лабораторной работы (статус Solved).

## Влияние на бизнес (Impact)
-	Полная компрометация конфиденциальности данных - злоумышленник может прочитать любые таблицы базы данных, доступные учётной записи СУБД, используемой приложением.
-	Компрометация учётных записей пользователей, включая административные, что открывает путь к дальнейшему повышению привилегий внутри приложения.
-	В зависимости от СУБД и прав пользователя приложения - потенциальная возможность модификации или удаления данных.
-	Репутационные и юридические риски, связанные с утечкой персональных данных пользователей.

## Рекомендации по устранению (Remediation)
### Основная рекомендация
Полностью исключить конкатенацию ("склеивание") пользовательского ввода в текст SQL-запроса. Использовать параметризованные запросы (Prepared Statements) с привязкой параметров (parameterized queries / bind variables) на уровне драйвера СУБД. Пользовательский ввод должен передаваться исключительно как значение параметра, а не как часть текста запроса.
#### Пример уязвимого кода (псевдокод):
query = "SELECT * FROM products WHERE category = '" + input + "'"

#### Безопасная реализация - Prepared Statement:
query = "SELECT * FROM products WHERE category = ?"
statement.setString(1, input)

### Дополнительные меры
- Применение принципа минимальных привилегий для учётной записи СУБД, используемой приложением (запрет доступа к системным таблицам, отсутствие прав на запись, если функционал этого не требует).
- Использование ORM-фреймворков с безопасными по умолчанию механизмами построения запросов.
- Валидация и приведение типов входных данных (allow-list подход) на стороне сервера.
- Внедрение WAF (Web Application Firewall) в качестве компенсирующей меры, но не как замену исправлению кода.
- Хранение паролей исключительно в виде надёжных хешей с солью (например, bcrypt/argon2), чтобы даже в случае утечки данных пароли не были скомпрометированы в открытом виде.
- Регулярное проведение статического и динамического анализа безопасности кода в CI/CD-пайплайне.

## Заключение
Обнаруженная уязвимость представляет собой классический и при этом крайне опасный случай SQL-инъекции с возможностью извлечения данных из произвольных таблиц через технику UNION SELECT. Простота эксплуатации (отсутствие аутентификации, отсутствие дополнительных степеней защиты) в сочетании с высокой степенью воздействия на конфиденциальность данных обуславливает критический уровень риска. Рекомендуется приоритетное устранение уязвимости путём перехода на параметризованные запросы до следующего релиза приложения.
